## 二、★ 最容易踩坑的地方：accountId ≠ elderId

这是整个老人端的核心链路，**没想清楚就会写出到处查不到的 bug**。

```
elder_account.id  ──(elder_profile.account_id)──>  elder_profile.id
   (账户ID)                                          (档案ID/老人ID)
      │                                                    │
      ├── sys_message.user_id   ← 用 accountId            ├── service_record.elder_id
      ├── elder_profile.account_id                        ├── follow_up_record.elder_id
      └── JWT 里的 userId                                  ├── assessment_report.elder_id
                                                          └── elder_tag_relation.elder_id
```

**统一约定（我这边按这个写，写进 README）：**

1. **JWT 里存的 `userId` = `elder_account.id`（账户ID）**，不是档案ID。
2. 凡是查 `service_record` / `follow_up_record` / `assessment_report` / `elder_tag_relation`，都要先 `SELECT id FROM elder_profile WHERE account_id = ?` 换一次。
   - 我在 `ElderAccountService` 里提供 `Long getElderIdByAccountId(Long accountId)`，其他同学直接调。
3. `sys_message.user_id` 老人端 = `elder_account.id`。（见第六节待确认项 #3）
4. 现有 `ProfileMapper.selectElderProfileById` 里 `where elder_no=#{elderId}` 是错的，且参数是 `Integer` 应为 `Long` —— 属档案模块，我提醒同学改，不擅自改。

### 3.3 JWT + 用户上下文（重写现有拦截器）

现有 `LoginInterceptor` 有两个致命 bug（见 01 文档问题 6）：

| bug | 现状 | 修法 |
|---|---|---|
| `claims.get("userId", String.class)` | JJWT 0.12 存 Long 取 String **必抛异常** | 签发时**统一存 String**：`.claim("userId", String.valueOf(id))`，解析时 `Long.valueOf(claims.get("userId", String.class))` |
| 失败时 `writer.write("Token无效或已过期")` | 返回纯文本，前端 JSON 解析崩 | 输出 `{"code":500,"message":"登录已失效，请重新登录","data":null}`，状态码 401 |
| 只存 userId，不存 userType | 医生 token 能调老人接口 | claim 里加 `userType`，拦截器按路径前缀校验 |
| 拦截器被注释掉 | 全站裸奔 | 启用，放行 `/api/*/auth/**` |

新增文件：

```
src/main/java/com/cdut/
├── utils/JwtUtils.java        // generate / parse，密钥和过期时间读配置
├── utils/UserContext.java     // ThreadLocal<Long> userId + ThreadLocal<Integer> userType
└── interceptor/LoginInterceptor.java   // 重写
```

**★ `UserContext.clear()` 必须在 `afterCompletion` 里调用**，否则 Tomcat 线程池复用会串号（A 用户看到 B 用户的数据）—— 这是实训项目最常见的翻车点。

拦截器端隔离规则：

```java
// 路径前缀 → 允许的 userType
"/api/admin/"  -> 1
"/api/doctor/" -> 2
"/api/elder/"  -> 3
// 不匹配 → 500 "无权访问该端接口"
```

### 3.4 全局异常处理（重写）

新增 `BizException extends RuntimeException`，Service 里直接 `throw new BizException("账号或密码错误")`，处理器统一转 `Result.error(msg)`。

`GlobalExceptionHandler` 需要覆盖：

| 异常 | 返回 |
|---|---|
| `BizException` | `Result.error(e.getMessage())` |
| `MethodArgumentNotValidException` | `Result.error(第一个字段的 message)` |
| `ConstraintViolationException` | 同上 |
| `Exception`（兜底） | `Result.error("系统繁忙，请稍后再试")` + **打日志**（别把栈甩前端） |

### 3.5 分页工具 `PageResult<T>`

```java
@Data
@NoArgsConstructor
@AllArgsConstructor
public class PageResult<T> implements Serializable {
    private long total;      // 总条数
    private int  pages;      // 总页数
    private int  pageNum;    // 当前页
    private int  pageSize;   // 每页条数
    private List<T> list;    // 数据

    public static <T> PageResult<T> of(long total, int pageNum, int pageSize, List<T> list) {
        int pages = (int) ((total + pageSize - 1) / pageSize);
        return new PageResult<>(total, pages, pageNum, pageSize, list);
    }
}
```

### 4.2 `POST /api/elder/auth/register` — 注册

**Service 逻辑（`@Transactional`，两张表要么都成要么都败）：**

1. 校验手机号格式 `^1[3-9]\d{9}$`、身份证 `^\d{17}[\dXx]$`
2. **查重**：`bind_phone` 已存在 → "该手机号已注册"；`id_card` 已存在 → "该身份证号已注册"
3. 生成 `accountNo`：`"EL" + yyyyMMdd + 4位随机`，循环重试直到不冲突
4. 密码 BCrypt 加密后写入 `elder_account`：
   - `auth_status = 0`（待审核）
   - `account_status = 1`
   - `register_channel` 取入参，默认 1
5. 拿到自增 `id`，插入 `elder_profile`（`account_id`、`name`、`id_card`、`phone`、`status=1`，`elder_no` 同 `accountNo`）
6. 捕获 `DuplicateKeyException` → `BizException("该手机号或身份证号已注册")`

**返回**：`Result.success("注册成功，请等待审核", null)`

### 4.3 `POST /api/elder/auth/login` — 登录

**查账户（一个 SQL 覆盖三种账号）：**

```sql
SELECT a.* FROM elder_account a
LEFT JOIN elder_profile p ON p.account_id = a.id AND p.is_deleted = 0
WHERE a.is_deleted = 0
  AND (a.account_no = #{account} OR a.bind_phone = #{account} OR p.id_card = #{account})
LIMIT 1
```

**校验顺序（顺序很重要，影响提示语）：**

| 顺序 | 条件 | 返回 message |
|:--:|---|---|
| 1 | 查不到 | `账号不存在` |
| 2 | 查到多条（理论上不会） | `账号异常，请联系管理员` |
| 3 | `!bcrypt.matches(原密码, 密文)` | `账号或密码错误` |
| 4 | `authStatus == 0` | `账号待审核，请联系管理员` |
| 5 | `authStatus == 2` | `账号审核未通过，请联系管理员` |
| 6 | `accountStatus == 2` | `账号已冻结，请联系管理员` |
| 7 | `accountStatus == 3` | `账号已注销` |
| 8 | 通过 | 签发 JWT |

> ★ 顺序 3 必须在 4~7 之前 —— 先验证密码再验证状态，否则别人拿手机号就能试出某个账号的审核状态（信息泄露）。

**签发 JWT**：

```java
Jwts.builder()
    .claim("userId", String.valueOf(account.getId()))  // ★ 存 String
    .claim("userType", "3")
    .claim("accountNo", account.getAccountNo())
    .setExpiration(new Date(System.currentTimeMillis() + expire * 1000))
    .signWith(key)
    .compact();
```

`refreshToken`：接口文档定义了但**没有刷新接口** → 先返回与 `accessToken` 相同的值，并在 README 注明"暂未实现刷新"。

### 4.4 `POST /api/elder/auth/logout` — 退出

无状态 JWT 做不了真正的失效。方案：
- **简单版（推荐）**：返回 `Result.success("退出成功")`，前端自己删 token。
- 进阶：Redis 黑名单 —— 实训项目没 Redis，跳过。

### 4.5 `GET /api/elder/center/account` — 我的账户信息

- `userId` 从 `UserContext` 取，不从 request（约定见 01 文档第 9 条）
- 查 `elder_account` + 左连 `elder_profile` 拿 `name`/`photo_url`
- **置空 password** 后返回 `ElderAccountVO`
- 查不到 → `BizException("账户不存在")`

### 4.6 `PUT /api/elder/center/password` — 修改密码

1. `newPassword` 长度 6~20，且不能与 `oldPassword` 相同
2. `bcrypt.matches(oldPassword, 库中密文)` → false 抛 `原密码错误`
3. 新密码 BCrypt 加密后 `UPDATE elder_account SET password=? WHERE id=?`
4. **改完建议让 token 失效**（前端强制重新登录）—— 可选，跟前端约定

### 4.7 `GET /api/elder/center/messages` — 消息列表（分页）

Mapper 用 **XML**（动态 SQL，注解写 if 太丑）。新建 `src/main/resources/mapper/MessageMapper.xml`（`application.properties` 已配 `classpath*:mapper/*.xml`，但这个目录还不存在，要建）。

```xml
<select id="selectPage" resultType="com.cdut.pojo.SysMessage">
  SELECT * FROM sys_message
  WHERE user_id = #{userId} AND is_deleted = 0
  <if test="msgType != null"> AND msg_type = #{msgType}</if>
  <if test="isRead   != null"> AND is_read  = #{isRead}</if>
  ORDER BY create_time DESC
  LIMIT #{offset}, #{pageSize}
</select>

<select id="selectCount" resultType="long">
  SELECT COUNT(*) FROM sys_message
  WHERE user_id = #{userId} AND is_deleted = 0
  <if test="msgType != null"> AND msg_type = #{msgType}</if>
  <if test="isRead   != null"> AND is_read  = #{isRead}</if>
</select>
```

Service：`count` → `list` → `PageResult.of(...)`。

### 4.8 `PUT /api/elder/center/messages/{id}/read` — 单条已读

```sql
UPDATE sys_message SET is_read = 1 WHERE id = #{id} AND user_id = #{userId}
```

> ★ **必须带 `user_id` 条件**，否则改一条 id 就能把别人的消息标已读（越权）。
> 影响行数 0 → `BizException("消息不存在")`

### 4.9 `GET /api/elder/center/messages/unread-count` — 未读数

```sql
SELECT COUNT(*) FROM sys_message WHERE user_id = #{userId} AND is_read = 0 AND is_deleted = 0
```

### ⚠️ 遗留风险：sys_message 无 user_type 会串端

三端账户表（`sys_user` / `doctor_account` / `elder_account`）主键都是**独立自增**，都会从 1 开始。
管理端给"账户ID=1的后台用户"发消息，可能正好落在"老人 accountId=1"头上。

**低成本缓解（推荐，不用改表）**：给三端的自增起始值错开，例如

```sql
ALTER TABLE sys_user       AUTO_INCREMENT = 100000;  -- 管理端 1xxxxx
ALTER TABLE doctor_account AUTO_INCREMENT = 200000;  -- 医生端 2xxxxx
ALTER TABLE elder_account  AUTO_INCREMENT = 300000;  -- 老人端 3xxxxx
```

这样 ID 天然不冲突，也不用给表加列。**建议跟队长提一嘴，让管理端同学一起执行。**
